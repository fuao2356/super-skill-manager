# 技能架构方法论

基于付翱的工程管理自动化实践经验提炼。

## 什么是一个好技能（总纲，2026-08-05 定稿）

**核心标准：AI 一看就懂、一用就对。** 用户原话："很多技能用着用着就变成流水账了，有时候我都看不太懂更别说 AI 了"——流水账是渐变病，好技能要能抵抗它。

### 好技能的 5 条标准

1. **身份清晰**：frontmatter 五字段完整真实（触发词/功能/依赖/标签/状态）——它是谁、怎么叫醒、跟谁配合，一眼可知
2. **规范不流水账**：正文是"操作规范"（现在该怎么做），不是"历史记录"（某天发生了什么）。日期过程叙述是流水账，要提炼成铁律
3. **结构理想**：往"多模式入口 + Loop 循环"靠——一个技能管一个领域，按场景分模式；有反复执行的动作设计成自迭代循环
4. **本地化**：路径/浏览器/网络通道适配本机，有"本机环境注意事项"段
5. **可验证**：命令/脚本可跑，踩坑已提炼成规则（"用 C，别用 A/B"），不是"试了 A 不行 B 不行"

### 流水账症状（反向检查）
- 出现大量日期标记（"2026-XX-XX 发现/测试/拆分"）→ 过程叙述堆砌
- 步骤和记录混在一起 → 分不清"现在该做什么"和"当时发生了什么"
- 越来越长、信息密度越来越低 → 只进不出
- 用户/AI 都要花时间猜"这句是规则还是历史" → 失去可读性

### 优化方向（模式3 参照）
- **去流水账**：删日期过程叙述，保留结论（"某天试了A不行B不行C可以" → "用 C，别用 A/B"）
- **往理想架构靠**：多模式入口、Loop 循环、内容分层（frontmatter 身份 + 触发词入口 + 正文流程 + 踩坑铁律）
- **保真**：命令/路径/阈值/触发词一条不丢；无损压缩
- **吸收提取（2026-08-05 用户纠正）**：**流水账必然长出来**（技能被使用就会长出日期叙述/过程记录），不是缺陷——关键是**吸收提取机制**。两种吸收：①自动吸收（AI 从日志/执行记录/复盘提炼新经验补进技能）②讨论吸收（和用户讨论——**用户是唯一知道哪些坑还有用、哪些过时的人**）。**讨论是效率最高的吸收方式**：用户负责"什么重要"（方向），架构标准负责"怎么组织"（骨架/不流水账/多模式）——讨论 + 架构双保险，AI 单干容易提炼错重点。吸收时用本总纲组织，吸收进来的内容天然是好结构，不会变回新流水账。工作流完成后的复盘讨论，也是模式3 的触发方式。
- **⚠️ 讨论内容必须归类归位到骨架对应段（2026-08-05 用户两次纠正"你还是没有理解我的想法"）**：讨论提炼出的每一点，先判断它是什么性质，再放进骨架对应位置——**是流程/步骤 → 放「怎么用（工作流程）」；是规则/坑/数据口径 → 放「注意事项（关键铁律 & 已知坑）」；是验证方法 → 放「怎么算对」；是故障 → 放「出错了怎么办」**。**禁止把讨论内容单独建章节**（如把"截屏沟通"建独立 `### 截屏沟通` 是错的——它是协作流程，应并入「模式 B 补缺状态」工作流）。判断方法：这句是"怎么做"还是"别踩坑"？是"步骤"还是"规则"？归类错了就是结构跑偏。

### 技能固定骨架（方案式结构，2026-08-05 用户原话："技能和我方案一样也是需要好的结构 清晰明了的"）

**好技能 = 好方案**：施工方案章节固定（编制依据/工程概况/施工部署/施工工艺/质保措施），谁都写得像样；技能也应有固定骨架，谁建都不跑偏。

**必备 4 段（每个技能都有）**：
```
1. 我是谁（frontmatter 五字段：功能/依赖/触发词/标签/状态）
2. 什么时候用（触发词，description 前 57 字符）
3. 怎么用（步骤 / 模式入口）
4. 注意事项（本地化 / 踩坑铁律）
```

**按需 3 段（复杂技能才有，像方案的分部工程）**：
```
5. 怎么算对（验证方法 / 验收标准）     ← 对应方案"质量验收"
6. 出错了怎么办（常见坑 / 应急处理）   ← 对应方案"应急预案"
7. 产出什么（输出物 / 交付物）         ← 对应方案"工程成品"
```

对照：方案"编制依据"= frontmatter 身份；"工程概况"= 一句话描述；"施工部署"= 多模式入口；"施工工艺"= 正文流程；"质保措施"= 踩坑铁律；"附图附表"= references/scripts 支撑文件。

**为什么分必备/按需**：简单技能 4 段够用（不膨胀），复杂技能补全 7 段（像方案一样小工程简版、大工程详版）。骨架不是越长越好——加章节是为了清晰，不是为了堆内容。

### 健康判定：基础款 / 高端款（2026-08-05 用户定义）

**检查技能健康度时对照骨架判定，别只看有没有流水账**：
- **基础款 = 必备 4 段齐全 → 就算健康**（我是谁/何时用/怎么用/注意事项）
- **高端款 = 基础款 + 按需 3 段（加分项，复杂技能才有）**
- **判定原则**：有基础款 = 健康。缺按需段（验证/出错/产出）**不算不健康**——那是加分项。简单技能 4 段够用，**给简单技能强行加按需段 = 违背"简单技能不膨胀"**
- 检查方法：grep 各段标记词逐项判定（是谁=frontmatter、何时用=triggers、怎么用=步骤/流程、注意=踩坑/本地化；按需：算对=验证/测试、出错=错误/排查、产出=输出/交付）

**优化时往骨架靠**：正文按"身份→入口→流程→铁律"组织，不把历史记录（会议纪要式）塞进工艺步骤。用户作为总工的本能：方案写得好不好一看结构就知道，技能同理。

### 结构化 Frontmatter（= 摘要 + 关键词，2026-08-05 用户洞察："其实这就是一个摘要和关键词嘛"）

每个技能的 SKILL.md 的 YAML frontmatter 必须包含五字段（用户已批准全库登记）：

```yaml
---
name: skill-name
description: 一句话 + 触发词（系统唯一真读字段，触发词必须在前 57 字符内）
tags: [领域, 功能]          # 2-4 个，粗粒度
function: 主语+动作+对象     # 一句话核心功能，≤40 字（用于去重）
dependencies: [skill名或工具名]  # 技能依赖用技能名，工具用命令名
triggers: [触发词1, 触发词2]  # 2-5 个，贴近用户说话原话
status: active              # active | experimental | deprecated
---
```

#### 字段规则

| 字段 | 规则 | 解决什么问题 |
|------|------|-------------|
| description | 系统触发唯一真读；触发词必须放前 57 字符内 | 技能入口路由 |
| tags | 2-4 个粗粒度标签，按领域/功能分类 | 按主题检索 |
| function | 一句话「主语+动作+对象」，≤40 字 | 技能去重 |
| dependencies | 技能依赖写技能名，工具依赖写命令名 | 关系图谱/断链检查 |
| triggers | 2-5 个，用用户说话的原话/场景 | AI 加载后确认场景 |
| status | active（在用）/ experimental（试验）/ deprecated（废弃） | **自我纪律标签，系统不读**（见下方状态机警示） |

#### 状态机（status 切换规则）
- 新技能/自创技能 → **默认 `experimental`（试验）**（2026-08-04 用户拍板：不本地化不算服役）
- **experimental → active 的门槛**（模式1 完成才转）：
  - dependencies 非空且内容真实（工具装了/技能存在）
  - 有"本机环境注意事项"段落
  - 触发词与现有技能无冲突
  - 功能与现有技能无重复
- 稳定使用 → `active`（服役）
- 被替代/过时 → `deprecated`（废弃，不再触发）
- 切换权：AI 建议，用户拍板；体检时发现 deprecated 技能标记待删
- **铁律**：AI 无意识自创的技能默认 experimental，本地化完成才转 active（用户拍板 2026-08-04）

**⚠️ status 是自我纪律，不是系统强制（2026-08-05 源码查证）**：Hermes 技能加载链路（agent/skill_utils.py）**不读 frontmatter 的 status 字段**。experimental/deprecated 标签触发词命中照样加载执行。系统只通过路径排除：`EXCLUDED_SKILL_DIRS` 含 `.archive/`——**想真不加载，deprecated 技能必须移入 `.archive/` 目录**，光改 status 字段没用。experimental 的正确语义 = AI 加载后看到标签要谨慎执行、先跟用户确认，不是系统拦。别向用户承诺"experimental 不加载"。

#### 触发词两层分工（关键）
- **系统层**：description 前 57 字符含概括触发词（决定技能会不会被看到）
- **AI 层**：frontmatter triggers 详细列触发场景（加载后确认）
- 触发词要查重：两个技能触发词重叠会抢加载（super-skill-manager 模式2 定时维护时扫）


## 多模式技能架构（用户推崇，2026-08-05 确认）

**用户喜欢的技能形态**：一个技能管理一个领域，内部按场景分多个模式入口。模式是"入口"不是"副本"——共享一个 frontmatter，但正文按模式分区。

**现有范例**：
- `construction-plan`（施工方案）— 多模式入口：编制方案/施工组织设计/专项方案
- `super-skill-manager`（技能管理）— 模式1 本地化 / 模式2 维护 / 模式3 优化
- `engineering-paper`（写论文）— 分阶段流程

**为什么好**：
- 触发词收敛为一组（"方案/论文/技能管理"），不碎片化
- 一个技能解决一类问题，不拆散
- 用户说"方案" → 一个技能覆盖所有方案类型，不用记哪个子技能

**判断标准**：同一领域的多个场景 → 合成一个多模式技能；不同领域 → 分开。别把"子模式"拆成"独立技能"（碎片化是死技能来源之一）。

## 技能 = Loop Engineering 循环

技能不应是"一次性执行"的死脚本，而应设计为**自迭代系统**：

```
用户定质量目标
  ↓
技能自动执行
  ↓  创作者/审查者分离
自动验证结果
  ↓  不达标则重试
调整参数/方法重试
  ↓  达标或收敛停止
输出最终报告
```

参考 `loop-engineering` skill 的具体实现模式。

## 外部技能本地化审计（中国化）

**任何外部/通用技能接入前，先做本地化审计，不要拿来就用。**（用户 2026-08-01 强调："技能需要社会主义的中国化"）

> 外来技能是理论，不结合本地实际就水土不服。不要假设工具装了、网络通了、服务能用了。踩过坑就固化到技能里，下次不再试错。

### 审计 4 步
1. **工具检查**：依赖命令装没装、登录没登录（`command -v` / whoami）
   - ⚠️ **工具 doctor 报错不一定是真坏**：看到 doctor FAIL 先实测功能，别急着下"工具不可用"结论（实测案例：agent-browser doctor 报 "No Chrome binary found" 但运行时自动发现浏览器，open/read 完全正常）
2. **网络通道测试**：依赖 URL 逐个 `curl -w "%{http_code}"`（200/302=通，000=被墙）
3. **本地替代**：查 **`<WIKI_ROOT>\skills-wiki\concepts\能力清单.md`**（唯一正本，记录"技能要求 → 本机替代"：Google→必应、Chrome→Edge、Jina→agent-browser 等）——替代关系以能力清单为准，不在本参照重复维护
4. **固化结论**：写进技能"本机环境注意事项"段，下次直接按记录走
